# 协议

> 字段级定义以 [`spec/openapi.yaml`](../spec/openapi.yaml) 为唯一真源。
> 本文只讲**为什么这样定**、**各端必须做什么**、**出错时怎么退化**。

## 1. 为什么要把协议单独拎出来

四个端（Android TV、iOS、macOS、Web）加一个服务端，如果各自对着需求文档写，
两周后会有四套字段名：`img` / `image` / `url` / `src`，`subject` / `科目` / `course`。
所以先把契约冻结成 OpenAPI，各端只对着它写，改协议必须先改这个文件。

一条纪律：**任何一端发现协议不够用，改 `openapi.yaml` 并说清理由，不要在自己的代码里偷偷加字段。**

## 2. 三层分离，这是整个架构的骨架

| 层 | 接口 | 职责 | 谁调 |
|---|---|---|---|
| **接入层** | `POST /api/ingest` | 收文件、落盘、写一条 `pending` | 上传端（iOS / macOS / Web） |
| **识别层** | 后台流水线 + `POST /api/batch/{id}/rerun` | OCR、分科、写 `item` | 服务端自己，不对外 |
| **呈现层** | `GET /api/day`、`GET /api/days` | 只读聚合 | 电视端、调试页 |

分离带来的两个直接好处：

- **上传端提交即忘**。`/api/ingest` 只做磁盘 IO，返回是毫秒级。用户点完就能关页面。
- **重跑免费**。图片在磁盘上，`item` 只是派生数据。换 OCR 引擎、改分科 prompt、模型抽风，
  对历史批次 `rerun` 一遍即可，永远不用让用户重新上传。

## 3. 状态机

```
                  ┌──────────────────────────────────────┐
                  │                                      │
   ingest         ▼          OCR 成功        分科成功      │
  ────────►  pending  ──►  ocr  ──►  parsing  ──►  done   │
                  │           │           │              │
                  │           └───────────┴──►  failed    │
                  │                              │        │
                  └────────── rerun ◄────────────┘        │
                              └───────────────────────────┘
```

规则：

- `pending` 是「图已经在磁盘上」，不是「什么都没发生」。所以 `failed` 的批次**原图依然可读**。
- `rerun` 只允许对 `failed` 和 `done` 发起。对 `pending/ocr/parsing` 发起返回 202 但忽略（幂等）。
- **客户端不要按 status 值写死 UI**。只需要判断一件事：`status == done` 才有 `subjects`，
  其余情况一律退化成「只看图」。

## 4. 各端职责矩阵

| 能力 | TV | iOS | macOS | Web | 服务端 |
|---|---|---|---|---|---|
| 上传多图 | — | ✅ | ✅ | ✅ | 接收 |
| 粘贴截图 | — | ✅（读剪贴板） | ✅（Cmd+V 监听） | ✅（paste 事件） | — |
| 看最近批次 / 状态 | — | 只读不展示 | 只读不展示 | ✅ | 提供 |
| 重跑 / 删除 | — | — | — | ✅ | 执行 |
| 读某天作业 | ✅ | — | — | ✅（调试页） | 提供 |
| 日期条圆点 | ✅ | — | — | ✅（调试页） | `/api/days` |
| 全屏看原图 | ✅ | — | — | ✅ | `/img` |
| OCR / 分科 | — | — | — | — | ✅ |
| 定时抓 QQ 群 | — | — | ✅（Codex 走 UI 自动化） | — | 接收 |

三个刻意的「不」：

- **iOS 不做查看界面**。手机上看作业是本末倒置——手机就是那个「大人不肯给」的东西。
  iOS 端只有一个功能：把图传上去，然后关掉。
- **macOS 不做查看界面**。同上，它只是个采集入口。
- **TV 不做上传**。电视上输入路径、选文件是灾难。TV 只读。

## 5. 客户端必须实现的四件容错

这四条不是「锦上添花」，是决定产品能不能用的底线。

1. **图优先，文字垫底**
   原图是唯一可信来源，OCR 必有错。任何时候原图都要能看，文字区永远带一句
   「识别结果，仅供参考 · 以原图为准」。识别整条链挂了，产品退化成「看图」，仍然可用。

2. **`empty` 和 `pending` 必须分开显示**
   - `empty` → 「今天还没有作业 / 老师发出来之后，这里会自己出现」
   - `pending` → 显示原图 + 「正在识别」

   混成一个状态，孩子看到「没有作业」就走了，而实际上作业已经在系统里。

3. **超时按「宁可显示旧的」处理**
   电视端先渲染本地缓存的上一份数据，再后台刷新。网络断了也必须有东西看，
   哪怕标题上标一句「上次更新 17:32」。

4. **上传端不等待**
   `POST /api/ingest` 返回 202 就清空表单、弹一句「收到 3 张，处理完电视上就有」，
   然后让用户走。千万不要在页面上转圈等 OCR——识别 5–15 秒，用户等一次就不想再用。

## 6. 日期与时区

- 所有日期字符串 `YYYY-MM-DD`，语义是 **Asia/Shanghai 的那一天**。
- 服务端不接受客户端传 UTC 时间戳来推断日期，避免「晚上 23:50 上传被算成第二天」。
- 上传端的日期选择器默认当天，允许改成前几天（补传昨天的作业是真实需求）。
- `days_ago` 由服务端计算，客户端不要自己用本地时钟减——电视的系统时间经常是错的。

## 7. 错误处理约定

统一返回：

```json
{ "error": { "code": "invalid_date", "message": "日期格式应为 YYYY-MM-DD" } }
```

| code | HTTP | 客户端应该做什么 |
|---|---|---|
| `bad_request` | 400 | 提示 message，不重试 |
| `invalid_date` | 400 | 同上 |
| `too_many_files` | 400 | 提示「一次最多 6 张」，让用户删几张 |
| `file_too_large` | 413 | 提示「单张不能超过 20MB」 |
| `unsupported_type` | 415 | 提示支持的格式 |
| `not_found` | 404 | 静默（列表项可能已被删除） |
| `ocr_failed` | 500 | 显示「没识别出来」，给重跑按钮 |
| `llm_unavailable` | 502 | 同上，文案改成「识别服务暂时不可用」 |
| `internal` | 500 | 提示并记录 |

`message` 是中文、可直接展示的句子。客户端不要自己拼错误文案，也不要用 `code` 去猜。

## 8. 部署与地址

- 服务端**不感知自己的外网地址**，所有 URL 都是相对路径，客户端自己拼 base。
- 各端的 base URL 存在本地设置里，默认 `http://nas.local:8080`。
- 仅局域网，不做公网映射。图片里有别人家孩子的名字。
- 无鉴权。如果以后要开公网，加一个固定 `X-Token` 头，服务端校验即可，不要上 OAuth。

## 9. 演进策略

- 加字段：随时加，客户端必须容忍未知字段（不要用严格 struct 解码到 map 再报错）。
- 删字段 / 改语义：必须同时改 `openapi.yaml` 的 `info.version`，并在本文档记一条变更。
- 不引入版本号路径（`/v1/`）。这是自用工具，只有一个服务端和一个客户端团队（你），
  版本路径只会增加心智负担。破坏性变更直接改，反正两端一起发。

# 方案

## 1. 总体架构

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  Android TV │   │   iPhone    │   │   Mac mini  │
│  原生 App   │   │  SwiftUI    │   │  Codex 定时 │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │ GET /today      │ POST /ingest    │ 截图 + POST /ingest
       │ (读)            │ (写)            │
       └─────────────────┼─────────────────┘
                         ▼
              ┌──────────────────────┐
              │  NAS · Go 服务 :8080 │
              │  ├─ 原图存储 (磁盘)  │
              │  ├─ OCR 适配层       │
              │  ├─ 分科 (LLM)       │
              │  └─ SQLite          │
              └──────────────────────┘
```

所有客户端都是「薄」的：电视端只读，上传端只写。**没有任何业务逻辑放在客户端**——换 OCR、改分科规则、调 prompt，都不用重新发版。

## 2. 数据流

```
1. 老师发图到 QQ 群
2. 采集：Mac mini 落图 → POST /ingest（或网页手动传）
3. 服务端：存原图 → 写 batch(pending) → 立即返回 202
4. 后台：OCR → 合并老师配文 → LLM 分科 → 写 item → batch(done)
5. 电视：启动时 GET /today → 渲染
```

**关键：3 和 4 之间是异步的、可重入的。** 「入库」和「识别」是两个独立步骤，所以识别失败重跑是免费的。

## 3. 关键决策

### 3.1 入库与识别解耦

`/ingest` 只做两件事：存文件、写一条 `pending` 记录。识别由后台 worker 做，也可以对任意历史 batch 重新触发。

**理由**：OCR 和 LLM 都会变。换引擎、改 prompt、修 bug，都需要能把历史数据重新跑一遍。如果识别写在上传流程里，历史数据就废了。

### 3.2 不做推送，只做拉取

电视 App 在启动 / 唤醒时 `GET /today`，服务端不主动推。

**理由**：电视待机后网络连接会断，长连接和推送都不可靠；而「打开就有」本身已经够快。轮询也够用——打开时拉一次，页面停留时 5 分钟拉一次。

### 3.3 图为主，文为辅

原图占 60% 宽度，OCR 文字占 40%，文字区底部固定一句「识别结果，仅供参考」。

**理由**：黑板照片的 OCR 一定会有错字。错字本身不致命，但如果家长以为文字就是原文，信任就没了。所以图永远在，且永远更大。

### 3.4 AI 只做「结构化」，不做「判断」

- LLM 负责：把散行文字切分成科目和条目、理解老师的口语表述
- LLM 不负责：判对错、算答案、生成题目

**理由**：孩子用的东西，模型算错一道题的代价远大于它带来的便利。

### 3.5 电视端原生，不做 Web

**理由**：TV 浏览器版本差异大、遥控器焦点行为不可控、图片缩放体验差。原生 Compose for TV 的焦点系统是现成的，且能本地缓存图片。

网页版只保留一个用途：**接口验证和应急**（手机上传页 + 浏览器看作业）。

### 3.6 采集做成可替换的 Source

```
type Source interface {
    Fetch(ctx, date) ([]Image, error)
}
```

实现可以是：`qq-mac`（Codex + Computer Use）、`web-upload`、`nas-folder`（手动丢文件）。

**理由**：QQ 这条通道会变（客户端改版、登录失效、风控）。接口固定住，换实现不影响其他部分。

## 4. 技术栈

| 模块 | 技术 | 备注 |
|---|---|---|
| 电视端 | Kotlin + Compose for TV | minSdk 21，`adb install` 侧载 |
| iOS / macOS | SwiftUI | 共享上传逻辑，图片压缩用 ImageIO |
| 服务端 | Go 1.22+ / `net/http` / `modernc.org/sqlite` | 纯 Go，免 CGO，可交叉编译到 ARM |
| OCR | 云 API 起步（腾讯云 / 百度，有手写体接口）；稳定后考虑 PaddleOCR 本地 | 一天几张，成本可忽略 |
| 分科 | 任意 LLM，JSON Schema 约束输出 | 失败降级为「一张图一个卡片」 |
| 部署 | NAS 上 docker 或 systemd，监听 8080 | 只在局域网 |

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| QQ 采集通道失效（登录过期 / 改版） | 当天没有作业 | 网页手动上传兜底；人本来就在回路里 |
| 黑板照片 OCR 质量差 | 文字不准 | 图永远在；文字标「仅供参考」 |
| 电视不是 Android | App 装不上 | 提前确认；退化为浏览器链接 |
| 分科错误 | 科目张冠李戴 | 保留原图；条目顺序按图片顺序 |
| 重复上传 | 电视上出现重复卡片 | 文件名带时间戳，P2 再做 hash 去重 |

## 7. 不做的事（架构层面）

- 不引入消息队列、不做微服务、不做 Redis
- 不做用户体系与权限
- 不做前端框架与构建工具（网页端保持单文件）
